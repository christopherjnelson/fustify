# Authoritative multiplayer

Fustify multiplayer is a registered-account, human-only mode for 2–5 players.
Every room begins as an editable private waiting room. Its host may keep it
private, start it privately, or irreversibly publish its final configuration as
a public lobby. Private rooms use room codes; public rooms use canonical direct
URLs and never expose or accept a room code.

The mode reuses the local deterministic generator, setup code, `gameReducer`,
globe, minimap, navigator, accessible phase controls, and victory rules.
Multiplayer is considered playable only after the PostgreSQL/API tests and a
complete two-browser winner test pass.

## Routes and lifecycle

- `/multiplayer` requires an email/password Fustify account and renders public
  waiting rooms plus private create/join controls.
- `/multiplayer/room/:roomId` is the pre-game lobby. Each member may claim one
  human seat. Start requires at least two claimed seats. A host leaving closes
  the room; a non-host leaving releases their seat and membership.
- `/multiplayer/match/:matchId` restores the canonical persisted world and
  mutable match snapshot. It never invents ownership or combat results locally.

New rooms default to 42 territories and 6 continents. The host selects 12–48
territories, 2–6 continents, 2–5 seats, and a seed. Multiplayer accepts random
assignment only. There are no bots, takeover, mid-match joins, spectators,
matchmaking, started-game browsing, chat, timers, kicking, or host migration.

Public discovery returns presentation fields for public rooms still waiting
for players and never returns a join code, user ID, email, private room, or
started/closed room. Joining locks and rechecks the room, membership, and
capacity. Publishing is irreversible: the API locks and validates the room,
then changes visibility and clears the private code in one transaction.

Public cards use deterministic same-origin SVG previews generated by the API.
Room creation, setting persistence, and publication do not depend on thumbnail
delivery.

## Authority boundary

Browsers call same-origin Node API routes with their Better Auth session. The
API resolves membership and seat, locks canonical rows, validates actor, turn,
revision, idempotency key, and exact `GameAction`, then invokes the shared
platform-neutral `gameReducer`. Clients may select legal attack dice but cannot
submit rolls, casualties, ownership, winners, or resulting state.

Match initialization uses the same boundary. The service generates and stores
the complete `PlanetDefinition`, starting ownership and armies, player order,
turn state, combat sequence, events, and initial fingerprint before clients
enter the match. A launch lease prevents duplicate starts and can be recovered
after an abandoned request.

Database credentials and the Better Auth secret are server-only. Browser code
never connects to PostgreSQL and receives no database or privileged service
credential.

## Durable command protocol

`matches` contains immutable setup/seat/generator/planet snapshots and the
mutable canonical snapshot, revision, SHA-256 fingerprint, last command type,
status, and winner IDs. `match_commands` is an append-only audit of accepted
commands containing the actor, seat, command, payload hash, idempotency key,
previous/resulting revision, fingerprint, and server timestamp.

Each command uses a UUID idempotency key. Repeating the same key, actor,
expected revision, and payload returns the existing result without another
transition. Reusing the key for different input is `idempotency_conflict`; a new
key with an old revision is `revision_conflict` and the client refetches.

Activity reactions are persistent social metadata outside the gameplay
protocol. Each participant may set or clear one `fire`, `laugh`, `heart`, or
`angry` reaction per canonical event.

## Client synchronization

Only the active seat gets enabled gameplay actions. Submissions are not applied
optimistically. Accepted responses and periodic polling trigger canonical
refetches and whole-state replacement. Each route polls only its current room or
match, refetches on focus/online events, and ignores older or duplicate
revisions. Polling is an invalidation hint; persisted API state is always the
source of truth.

Reactions use a separate poll and never replace gameplay events, increment the
gameplay revision, reorder activity, or move the camera. Presentation-only
action cues and Follow Action likewise never change canonical state.

## Verification

```bash
pnpm test
pnpm test:e2e
pnpm test:visual
pnpm bundle:check
```

API tests cover non-member, unseated, and out-of-turn denial; stale revisions;
and duplicate/reused idempotency keys. Desktop Playwright coverage drives the
UI through create, join, seat claim, start, gameplay phases, refresh, and
completion. Mobile coverage checks restored-match readability and clipping.

For a production smoke test, use two isolated browser profiles: create and join
a two-seat room, claim both seats, start, compare revision and fingerprint,
complete actions from both accounts, refresh and reconnect, then confirm both
clients converge on the same winner and final fingerprint. Capture API and
PostgreSQL logs plus the match ID and last agreed revision for any failure.
